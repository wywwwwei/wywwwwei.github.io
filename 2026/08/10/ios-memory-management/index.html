Crossing the Memory Model Boundary: How Multiple Languages Coexist in a Single iOS App

Posted on 2026-08-10 In Concepts Word count in article: 2.2k Reading time ≈ 8 mins.

In a modern iOS app, Swift, Rust, C++, and Kotlin may all run at once—each with a fundamentally different memory management mechanism. Memory problems in mixed-language architectures are often not about any one language being written poorly; they stem from the boundary design between languages going wrong. This article takes an operating system’s perspective to examine the essential differences between these memory models, how multiple runtimes coexist within a single process, and the real-world memory side effects—and coping strategies—in a mixed-language architecture.

1. Essential Memory Management Comparison Across Five Languages

Language Core Mechanism Runtime Involvement Safety Guarantee Typical Overhead
C++ Manual management + RAII + smart pointers Virtually none Weak (convention-based) Very low (controllable)
Objective-C ARC (reference counting) Lightweight runtime Moderate Moderate (atomic operations)
Swift ARC + value-type copying Lightweight runtime Relatively strong Moderate
Kotlin (JVM) Garbage collection (GC) Full JVM/ART Strong Higher (potential pauses)
Kotlin/Native Own GC Own runtime Strong Moderately high
Rust Ownership + borrow checking Virtually none Extremely strong (compile-time) Very low (zero-cost)

You can think of this table as three camps. C++ / Rust push work to compile time or explicit programmer code, with the runtime barely involved in deciding whether an object is alive. Swift / Objective-C rely on the compiler to automatically insert retain/release, with the runtime providing only lightweight support (atomic reference counting, zeroing weak references, Autorelease Pool, etc.). GC-based languages like Kotlin (JVM) require a full runtime to manage the heap and perform collection.

There’s a detail here that’s easy to overlook: Swift’s value types (struct, enum) are stack-allocated by default, and only heap-allocated via copy-on-write when sharing is needed. Many developers coming from Objective-C habitually assume everything lives on the heap, but Swift’s design in this regard is actually closer to C++ semantics.

Where does ARC’s retain/release cost actually come from?

Swift/Objective-C reference counting is atomic by default—every retain/release is an atomic increment/decrement, which triggers CPU cache-line synchronization in multithreaded environments. When large numbers of small objects are created and destroyed on hot paths, this overhead can accumulate to a measurable degree. This is where Rust’s zero-runtime-overhead ownership model has an advantage in extreme performance scenarios.

2. How These Languages Are Used on iOS

  • C++ / Objective-C / Swift: Native support; can be directly mixed in compilation.
  • Kotlin: Compiled into a framework via Kotlin Multiplatform (KMP) for interoperation with Swift.
  • Rust: Compiled as a static library with UniFFI-generated bindings—a very mature approach. Mozilla components and numerous commercial SDKs use this in production.

UniFFI’s core value: the APIs you call in Swift look nearly native, but the actual computation runs in compiled Rust machine code. However, “looks native” doesn’t mean “free”—data needs to be converted at the boundary. Numeric and boolean types are passed directly, with negligible overhead; strings are passed via a UTF-8 pointer plus length, also fine; but if you pass a deeply nested struct, UniFFI will serialize it into a byte buffer, and that temporary allocation is absolutely visible in Instruments on hot paths. Rust types exported as Objects maintain their lifecycle across the boundary via handles plus reference counting—if this part of the design isn’t handled well, I’ll get to that later.

3. What Does the Operating System Actually Manage

With so many runtimes squeezed into one process, wouldn’t the OS help coordinate them? Not at all. iOS’s XNU kernel is responsible only for:

  1. Providing each process with an independent virtual address space
  2. Providing physical memory pages on demand (page faults)
  3. Memory permission protection
  4. Compression and Jetsam (process killing) under memory pressure
  5. Unconditionally reclaiming all memory when a process exits

No matter how many languages and runtimes an app contains, they are just one process in the eyes of the OS. All code shares the same address space and ultimately requests memory from the kernel via the system allocator. Language-level reference counting, ownership checking, and garbage collection are all intra-process concerns.

4. What Exactly Is a Language “Runtime”

If I had to summarize in one sentence: true garbage collection almost inevitably requires a runtime, pure reference counting can be made very lightweight, and compile-time ownership can reduce runtime overhead to near zero. But that’s too abstract—there are a few noteworthy specifics for each language:

  • Kotlin/Native has no JVM but has its own native runtime and heap. Since Kotlin 1.7.7 it uses a concurrent mark-sweep GC, and in most scenarios manual autoreleasepool calls are no longer needed during Swift interoperation (though explicit use is still recommended in extremely memory-sensitive scenarios).
  • Swift / Objective-C have no traditional large runtime + GC; the runtime only provides lightweight support such as atomic operations, weak reference tables, and Autorelease Pools.
  • C++ / Rust have virtually no language-level memory runtime. C++'s new/delete ultimately go to the system allocator, and smart pointers are standard library behavior; Rust’s ownership and borrowing are fully checked at compile time, and Rc/Arc are merely library implementations.

They share the address space and OS resources, but each manages its own objects and heap, interacting through well-defined boundaries. The typical structure looks like this:

The coexistence is held together by several mechanisms: each runtime typically only recognizes objects it allocated—Runtime A’s GC doesn’t scan Runtime B’s heap, which is logical isolation. Data transfer often requires copying or conversion; object references are held indirectly via handles or proxy objects, and a core job of the code generated by UniFFI and KMP is maintaining these cross-model lifecycle protocols. Each runtime may have its own GC threads or background tasks, but they are ordinary user-space threads, uniformly scheduled by the OS.

The real risks are concentrated at the boundaries: mishandled circular references cause leaks, one side releasing while the other still uses causes crashes, and disagreements about whether “the object is still alive” also cause problems.

6. Side Effects of Mixed Memory Models and How to Cope

Kotlin Multiplatform (Kotlin/Native): Main Side Effects

Periodically elevated memory footprint is the most obvious problem. GC reclaims lazily—objects are not freed immediately after becoming unreachable, but wait for the next GC cycle. High-frequency allocation produces a sawtooth memory pattern; short spikes may trigger Jetsam (especially in Extensions, background execution, and on low-end devices).

Coordination issues with Swift ARC are the most common source of problems. The two sides disagree on whether “the object is still alive”—Swift looks at reference counts, Kotlin/Native looks at GC reachability. Improper handling of bridging objects, closure captures, singletons, and global state easily causes cross-boundary leaks (a common symptom: Android is fine, but iOS memory keeps climbing).

There are also several milder but still real issues: GC threads consume extra CPU—modern implementations have improved significantly, but brief pauses may still occur; framework size and the runtime itself contribute additional baseline memory overhead; and debugging difficulty increases—Instruments displays Kotlin objects less intuitively than pure Swift, and leak sources may be in the Kotlin heap, the bridging layer, or the Swift side, requiring back-and-forth between tools.

Rust + UniFFI: Main Side Effects

Rust has no GC, so the problems are much milder than KMP—centered on boundary design and temporary allocations.

Cross-boundary data conversion overhead is negligible in most scenarios, but frequently transferring large objects on hot paths can produce measurable spikes in temporary allocations and copies. Batching typically mitigates this kind of problem effectively.

Rust types exported as Objects maintain their lifecycle across the boundary via handles plus reference counting; poor design can cause leaks or delayed release. Debugging cost is also worth noting—call stacks span Rust and Swift, making investigation more complex than purely native code.

Cross-runtime concurrent access: When a Swift object is captured by a Kotlin/Native or Rust closure executing on another thread, it bypasses ARC’s thread-safety assumptions. Kotlin/Native’s GC, when scanning the object graph, will crash if it finds that an externally referenced Swift object has already been released. Practical advice: prefer passing value types or immutable data; if reference types must be passed, ensure lifecycle is explicitly managed by one side, with the other holding only weak references or handles.

Coping Strategies

The most important architectural principle is reducing dangerous interactions. Have shared code work with “data” rather than complex “object graphs”; prefer simple types, DTOs, and byte arrays. Control cross-boundary call frequency; batch multiple small calls into bulk operations. Clarify ownership at the API design stage: who creates, who holds, who releases—don’t let both sides feel responsible for managing the lifecycle.

For Kotlin/Native, several approaches that have proven effective in practice: use autoreleasepool appropriately to manage temporary objects; proactively break unnecessary references (weak references or explicit nil-setting) to avoid globals/singles holding large context-related objects long-term; use Instruments to compare memory footprint between pure native and KMP-integrated builds; and for extremely memory-sensitive scenarios (Extensions, background tasks), carefully evaluate whether KMP is appropriate.

For Rust + UniFFI, favor value passing and simple structures in interfaces; reduce long-term holding of large Objects. Batching is preferable to fine-grained frequent calls.

For monitoring, establish a memory footprint baseline: compare peak and steady-state memory for the same operation across pure Swift, KMP-integrated, and Rust-integrated builds. Watch for sustained memory growth after long-running sessions, background transitions, and repeated page entries. Run dedicated tests on low-end devices and memory-constrained scenarios—many problems only surface on an iPhone SE or under memory pressure.

For Kotlin/Native’s heap, Instruments can only see the total Kotlin runtime usage and cannot break it down to individual Kotlin objects. You need to use Kotlin-side memory dump tools or diagnostic interfaces provided by the KMP framework.

Decision reference

Approach Memory Side-Effect Risk Better Suited For Less Suited For
KMP Higher (GC footprint, boundary leaks, baseline) Business logic sharing, highly consistent two-platform logic Extremely memory-sensitive, high real-time requirements, Extensions
Rust + UniFFI Medium-low (mainly temporary allocations and boundary design) High-performance cores, encryption, parsing, algorithms Deep sharing of complex object graphs with Swift, frequent large-object transfer on hot paths
Pure native Lowest UI, system integration, memory-sensitive paths High cost of multi-platform redundant implementation

Conclusion

When sinking heavy logic into Rust or C++, prioritize performance-critical modules with clear boundaries; avoid frequently transferring complex large objects on hot paths. When using UniFFI or KMP, treat the bridging layer as a “translator between different memory models”—the quality of that translator directly determines whether two languages can coexist peacefully. When debugging memory issues, remember that Instruments shows the entire process’s usage; often the Leaks tool won’t catch the problem (e.g., leaks on the Kotlin heap), and you need to combine it with Kotlin-side dump tools.

The most important thing is to account for memory model differences at the architecture design stage, not as a post-launch fix.

At its core, memory management in a mixed-language architecture comes down to one simple question: who manages the life and death of objects, and who merely provides pages? Get that question straight, and you’ll avoid most of the pitfalls.
